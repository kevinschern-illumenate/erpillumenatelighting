# B2B portal product audit and roadmap

Prepared September 25, 2026. Repository baseline: `845979669b3760fa49a80dd7000892a3a327838e`.

Expanded September 25, 2026 with the product owner's four follow-up requirements: visual schedule product selection, complete other-manufacturer specification support, template → portal/Webflow → filled-submittal readiness, and the `/desk/illumenate-lighting` staff workspace. Existing priorities and the staff-approved buying model remain in force.

**Product recommendation:** make the next release a dependable, staff-approved B2B buying and project-management service. Complete the journey from product discovery through configuration, quote/PO submission, drawing review, and order follow-up. Give every supported product family the same standard of completeness. Repair data and workflow inconsistencies before expanding the number of exposed features.

This is a product investigation and roadmap for the next planning agent. It defines outcomes, priorities, scope, and acceptance criteria. It does not implement application changes or prescribe a detailed technical implementation.

**Scope and confidence.** The investigation traced portal routes, templates, JavaScript, APIs, DocType schemas, permissions, configuration adapters, schedule-to-order conversion, manufacturing components, document generation, notifications, and tests. It compared the current source with the existing portal, quotation/order, and configurator-grouping plans. Repowise's index matched HEAD; broad answers were generally weak or ambiguous, so substantive findings were checked against source. Historical health metrics were treated as maintenance signals, not evidence of runtime failures.

The supplied site, `https://app.illumenate.lighting/portal`, could not be inspected: browser inventory had no connected session, and the web tool could not access the URL. This is not evidence that the site is down. No authenticated visual review, production-data inspection, deployment comparison, or end-to-end live test was completed. The reported password-button failure remains a user-reported runtime defect with an unverified cause. Frappe is not installed locally; database-backed tests were not run. The 34 standalone LED-sheet math tests passed. Read-only probes also confirmed catalog/driver field mismatches, a missing kit-page implementation in this repository, and the order-conversion status-guard behavior described below.

The follow-up investigation also inspected the schedule Add Line/edit/upload paths, packet assembly, template-controller validation, the checked-in n8n workflow definitions, the public Webflow download dispatcher and the exported Desk workspace. Actual n8n executions, Webflow CMS/site bindings and deployed workspace customizations remain unverified. Findings about the checked-in workflow must be reconciled with the workflows actually installed.

Application code, production records, credentials, and site settings were not changed. This document is the only deliverable added by this investigation. Existing local work was preserved.

**The buying model is settled for this release.** The user selected: **dealers submit a quote request or PO/order request for staff approval**. A submitted request must never be presented as a confirmed order. Online payment and immediate automatic order confirmation are outside the initial release.

Existing repository decision records also specify a draft Sales Order as the durable order request, portal-only dealer usage, email notifications, company/project access boundaries, and four-family configuration alignment. Preserve these as planning constraints unless the product owner explicitly changes them. The earlier one-year retention preference needs definition by artifact type before it becomes an automatic deletion policy. The grouping plan contains additional recorded decisions; treat them as inherited scope, not as features that have already shipped.

**The main product problem is incomplete consistency across journeys.** The same product can encounter different forms, calculations, saving behavior, document sources, and wording depending on where the user starts. Some pages also offer controls whose visible promise exceeds the implemented behavior. A common visual style will help, but the release needs a common definition of what configuring, quoting, submitting, approving, and downloading mean.

Evidence labels below use **C** for source-confirmed behavior, **R** for user-reported runtime behavior, and **V** for a risk that requires deployment/data verification. A source-confirmed defect is not a claim that it was reproduced on the supplied live site. Evidence references E01–E30 at the end identify the relevant files and symbols.

Priority means:

- **P0 — release blocker:** can produce an incorrect commercial/manufacturing result or expose project documents beyond the intended audience. Resolve before expanding dealer usage of the affected journey.
- **P1 — required for a complete B2B release:** blocks a core task, misrepresents its outcome, or forces repeated staff intervention.
- **P2 — later improvement:** useful after the core journeys are reliable.

**Four complete customer journeys define the scope.**

1. **Discover a product with confidence.** A dealer finds a product by family, series/model or relevant specifications; sees useful imagery, dimensioned information, technical units, certifications, supported accessories and current documents; understands price and availability labels; and can start the appropriate configuration or standard-item request. A customer can distinguish a family datasheet from a configuration-specific submittal. Every published family has an intentional action, including inquiry-only products if engineering review is necessary.
2. **Build a request and obtain staff approval.** A dealer creates a project/schedule, configures products, sees quantities and the scope of power/accessories, saves, returns and edits without losing meaning. They either request a quote or submit a PO/order request. Staff receives a durable work item with all required information. The dealer sees a receipt and an honest status, reviews a versioned offer where needed, and receives an order acknowledgment only after staff approval.
3. **Submit and review drawings.** A dealer uploads one or more drawings against a project, schedule or order with purpose, notes and requested timing. The system verifies uploaded files, issues a receipt, assigns the request, and lets both parties exchange questions and revisions. The dealer downloads a clearly numbered revision and approves it or requests changes. Staff can distinguish technical customer signoff from authorization to manufacture.
4. **Manage the order after submission.** A dealer can find current and historical requests/orders, understand what needs their action, see confirmed versus estimated dates, monitor line-level fulfillment and partial shipments, and retrieve acknowledgments, packing/shipping documents and invoices according to access. They can request a change/cancellation or raise a linked issue. Reordering creates a new draft subject to current availability, pricing and approval.

Account access, password recovery, responsive layouts, clear errors and reliable notifications are required across all four journeys.

Two supporting journeys are also required for this expanded release. **Staff product setup:** create or revise a product through the appropriate template/specification/mapping DocTypes, validate readiness, preview its portal and Webflow representation, publish through n8n, and verify a filled submittal. **Mixed-manufacturer project documentation:** add ilLumenate and other-manufacturer lines to one schedule, preserve each line's metadata/documents and generate an overall specification packet. Other-manufacturer inclusion is a project-document capability; it does not by itself authorize ilLumenate to sell those products.

**Use business states that reflect real events.** The following are proposed customer-facing meanings, not instructions to add these exact enum values. The implementation planner should reconcile them with ERPNext document status, existing schedules and historical records.

| Business object | Recommended state progression | Required distinction |
|---|---|---|
| Quote request | Draft → Requested → Under review / Information needed → Quote issued → Accepted, Declined, Expired or Superseded | Requesting a quote does not mean staff has priced or issued it. “Quote issued” requires a specific offer, revision and validity period. |
| PO/order request | Draft → Submitted for approval → Under review / Changes proposed → Approved or Declined/Withdrawn | A PO is a customer's instruction, not proof that staff accepted price, delivery or terms. Approval creates the customer-visible confirmed order event. |
| Confirmed order | Approved → Production/Procurement → Partially fulfilled → Fulfilled → Closed, with holds/cancellation represented explicitly | Production, shipping, invoicing and payment are different facts. One aggregate badge must not erase partial fulfillment or open issues. |
| Drawing request | Draft → Submitted → Assigned/In progress → Waiting on customer → Revision published → Approved or Changes requested → Final/Closed | Approval identifies a specific revision. A new revision does not inherit approval silently. |
| Service issue | Submitted → Assigned/In progress → Waiting on customer → Resolved → Closed, with reopen available under a defined policy | Submission must have a trackable receipt and a response path, not just an email promise. |

Quote acceptance should route into the agreed staff-approved ordering process; it should not silently trigger production. For commercial documents, prefer extending the existing ERP Quotation/Sales Order lifecycle where it fits. ERPNext already models quotations with validity, prices and terms, followed by Sales Orders; the product gap is the coherent customer/staff experience around those records. [ERPNext quotation documentation](https://docs.frappe.io/erpnext/quotation).

Preserve the contents and commercial assumptions of issued quotations and approved orders. Edits after issuance need an explicit revision/change request and a visible approval history. Staff should see differences before approving them; dealers should see any changed price, specification or delivery commitment before accepting.

**S2A — Make product-authoring DocTypes and n8n/Webflow publishing dependable.**

Changes to shared attributes or templates should show affected products/mappings and require revalidation or regeneration as appropriate, while preserving historical approved configurations and documents.

Prevent a missing mapping from becoming an empty public field.
- Complete the checked-in n8n workflows or reconcile them with the installed versions: process all pending products beyond a single batch, update without duplicates, resume after partial failure, handle rate limits and timeouts, persist actionable error state, and retry without marking stale or failed content current.
